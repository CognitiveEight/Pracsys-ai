# Keel in this repository

`keel/` is a **plain copy** of the Keel knowledge-plane platform, taken so the
Keel-side work in the Agentic Ontology RAG programme can be done in this tree.

| Copied | 2026-08-24, 298 files, 239 Python modules, 2.6 MB |
| Excluded | `.git/`, `logs/*`, `__pycache__/`, `*.pyc`, `.pytest_cache/` |

There is **no git link to upstream.** Refreshing is a manual re-copy (below).
That was a deliberate choice — nothing here depends on `git subtree`/`submodule`
plumbing, and the working tree stays reviewable.

## This is still two systems

Copying the source co-locates the code. It does not merge the runtimes, and it
cannot: the two have **incompatible dependency pins**.

| Package | Keel | SimplerToday |
|---|---|---|
| fastapi | `>=0.136.3,<0.137.0` | `==0.109.0` |
| uvicorn | `>=0.34,<0.35` | `==0.27.0` |
| qdrant-client | `>=1.12,<2` | `==1.7.3` |
| redis | `>=5.2,<6` | `==5.0.1` |
| python-multipart | `>=0.0.18` | `==0.0.6` |

`httpx`, `pydantic` and `pydantic-settings` are the only shared packages whose
ranges overlap. So:

* **Do not `pip install` Keel into `env/`.** It will fight the AI service's pins.
* Keel gets its own virtualenv (or, normally, its own container).
* `python -c "import app.main"` from `keel/backend` fails under `env/` — that is
  expected, not a broken copy.

This matches Section 3.2 of the work plan, which specifies two planes talking
over REST/MCP rather than one process. The copy is a source-tree convenience,
not an architectural change.

```

    ontology/  statutes/  eval/    programme foundations (see AGENTIC_ONTOLOGY_RAG_FOUNDATIONS.md)
  keel/                      knowledge plane — vendored, editable

    backend/migrations/      Alembic
    docker-compose.yml       Keel's own stack (Postgres, Qdrant, Neo4j, Redis, MinIO)
    docs/                    Keel's documentation
```

`keel/` shares no top-level name with the AI service, which is why it is nested
rather than merged — `app/`, `docs/`, `logs/`, `docker-compose.yml`, `Dockerfile`,
`README.md`, `CLAUDE.md` and `AGENTS.md` all exist in both.

## The `.gitignore` trap

This repo's `.gitignore` has a bare `*.md` rule. Left alone it silently
swallowed Keel's entire `docs/` tree, `AGENTS.md`, `CLAUDE.md`,
`Keel_MVP_Scope_Document_v3.md` and `.github/` templates — 30 of the 298 files.
Negation rules were added at the end of `.gitignore`:

```gitignore
!keel/**/*.md
!keel/*.md
```

**If you re-copy Keel, re-check this.** `git status --porcelain --ignored keel/`
should list nothing.

## Running each side

```bash
# AI service (this repo's venv)
make run

# Keel (its own stack)
cd keel && docker compose up -d
```

Keel's compose file brings up Postgres, Qdrant, Neo4j, Redis and object storage.
Note it declares its **own** Qdrant and Redis, which collide on ports with this
repo's root `docker-compose.yml`. Run one or the other, or remap ports, until
the combined deployment compose of Phase 0 exists.

## Refreshing from upstream

```bash
rsync -a --delete \
  --exclude='.git/' --exclude='__pycache__/' --exclude='.pytest_cache/' \
  --exclude='*.pyc' --exclude='logs/*' \
  /path/to/keel-ai/ keel/

git status --porcelain --ignored keel/   # must be empty; see the .gitignore trap
```

Record the new upstream commit in the table above. Local edits to `keel/` are
overwritten by `--delete`; commit them first and re-apply, or drop `--delete`
and merge by hand.

## Local modifications to `keel/`

Changes made here, not upstream. **A refresh with `--delete` wipes these** — re-apply
them or the deployment silently reverts to broken behaviour.

| File | Change | Why |
|---|---|---|
| `backend/app/services/providers/gemini.py` | Added (work-plan task 1.1) | Gemini as a live LLM + embedding provider, so the knowledge plane stays on the existing Google relationship |
| `backend/app/services/provider_catalogue_service.py` | `live_provider_defaults()` reads `settings.*` instead of returning hardcoded `"openai"` | See below |
| `.env` | Generated by `scripts/keel_up.sh`; gitignored | Gemini providers, generated secrets, and `QDRANT_VECTOR_SIZE=3072` — Keel's default is 1536 (OpenAI) and `gemini-embedding-001` returns 3072 |
| `docker-compose.override.yml` | Generated by `scripts/keel_up.sh` | Host port remap — this machine's Neo4j/Redis already hold 7687/6379 |

### Why `live_provider_defaults()` had to change

Setting `EMBEDDING_PROVIDER=gemini` in the environment had **no effect**, and every
ingest failed with a 401 against OpenAI. Three upstream behaviours combine:

1. `extract_provider_config(workspace)` falls back to `live_provider_defaults()`
   whenever `workspace.settings` carries no provider keys — which is every
   workspace `scripts/seed_admin.py` creates.
2. `live_provider_defaults()` returned a hardcoded `{"llm_provider": "openai",
   "embedding_provider": "openai"}`, ignoring the configured settings.
3. `llm_gateway.embed()` lets that per-workspace value **override**
   `settings.embedding_provider`, so the hardcoded default wins over the env var.

And there is no way to correct it afterwards: `WorkspaceSettingsUpdate`
deliberately excludes `embedding_provider` ("changing the embedding model
requires full re-embedding … not an admin-UI toggle"). So a deployment configured
for Gemini embedded via OpenAI, unfixably, unless the fallback itself reads the
configuration. It now does. A workspace that has made its own explicit selection
is unaffected — only the fallback moved.

### The vector size must move with the embedding model

`qdrant_vector_size` defaults to **1536** (OpenAI) and is not in `.env.example`.
`gemini-embedding-001` returns **3072**, so leaving the default produces a
collection every upsert fails against *after* the embedding has already
succeeded and been paid for. `scripts/keel_up.sh` sets it from the
dimensionality its preflight actually measures, so the two cannot drift.

`init_collection` (called from `app/main.py` at startup) creates the collection
only when it does not already exist — it never resizes one. Changing the setting
on a deployment that has already booted therefore does nothing; the Qdrant
volume has to go, which is what `scripts/keel_up.sh --reset` does.

Note the failure is also misreported: `ingest_service._humanize_ingestion_error`
renders *any* provider 401 as "Check OPENAI_API_KEY and OPENAI_BASE_URL", whatever
the configured provider is. Read that message as "some provider returned 401".
